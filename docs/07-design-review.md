# 设计答辩与检查要点

## 真正需要解释清楚的设计

**Agent 的决策权在哪里？** 模型每轮收到真实观察后返回 Function Calling 或最终 JSON。
生产代码没有按主题、文档 ID、期限数字选择工具的分支。运行时只施加参数、预算、出处和已知候选核查约束。
失败重试、换查询、是否读取、何时请求澄清都由模型决定。真实路径见 Live Trace 的 model/tool 事件和 response_id。

**为什么单个文档引用真实，回答仍可能错？** 引用来源校验只能证明文字出现在哪里。
模型可能把预览中的另一条流程混入回答，也可能把版本日期扩展成生效日期。
这两类问题均在本次 Live 中实际发生。解决方式包括更明确的事实边界、同一 Agent 的最终复核，
以及独立的数字/禁止事实回归和补充语义审查，而不是把 substring 检查包装成语义保证。

**最终复核是不是第二个 Agent？** 不是。它仍在同一段对话、同一运行预算和同一工具循环中。
模型先给出候选，运行时要求按公开检查表再确认，模型可保留、改写或继续查证。
没有角色交接、独立 Agent 状态或第二条工具路线。ANSWERED/CONFLICT/NEEDS_CLARIFICATION 启用复核；
NOT_FOUND/TOOL_ERROR 可以直接结束，避免故障退出又被额外复核挤掉最后额度。
Mock 默认关闭此项，以保持脚本单测精确；单测显式启用覆盖同一机制。

**为什么不按最新日期解决冲突？** version_date 是版本标签，不能推出优先级或生效区间。
supersedes 明确且范围满足时才能解释替代链；范围不同则按当前问题与历史中的条件判断。
模型还必须区分“询问各部门对比”和“询问自己该遵守什么”，后者缺部门时需要澄清。

**为什么要求核查候选的所有片段？** 首版只检查“是否读过该文档的任意段落”。
这样读一个简介就可能绕过隐藏在另一段的冲突。当前小语料采用保守的全部片段核查门禁。
它不负责判定冲突，但会阻止用无关段落假装查完。代价是长文档可能耗尽预算，这是明确的扩展边界。

**检索改进有没有证据？** 普通小数据集的 Recall@5 两者都满分，不能声称普遍提升。
另设精确 ID 查询下的竞争文档发现压力集，保持同一资料，专门观察主题扩展是否能带回竞争制度。
该集合是针对机制设计的压力测试，不是随机盲测。数字分别报告，不混入通用指标夸大效果。

**MiniMax 接入有哪些真实差异？** 官方兼容接口要求多轮工具调用保留续接字段。
续接信息只在内存回传，不保存到 Trace。Trace 只保存实际模型名、response_id、finish_reason、token 用量和可观察动作。
JSON 模式可配置，因为兼容网关能力不同；没有自动切换到 Mock。API 限流和超时返回未完成状态，
可配置请求间隔和批处理间隔，不通过不可见的自动重试伪造成功。

## 提交前能展示的内容

- 单一来源、冲突、资料外、改写、追问、故障的真实输入/输出/Trace。
- 文档替换、删除、重命名及随机新期限，验证答案来自运行时资料。
- 已知部门与历史部门、多段竞争条款、明确替代链、持续读失败、一次搜索失败后的恢复、轮次耗尽。
- Prompt v1—v4 原文、对应失败记录、修改原因、最终复验，保留失败而不是只挑成功截图。
- pytest XML、基线/改进原始 JSON、补充语义审查的实际结果。

## 仍不应承诺

不承诺拿到某个分数；招聘方评分不受项目控制。不将少量合成案例的通过率描述成生产准确率。
不将同模型的补充语义审查当作独立真值。不将 Codex 的实现和测试写成候选人手工完成。
本人投入时间、人工复核内容和认可的技术决策须由候选人确认。
